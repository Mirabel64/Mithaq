# Proof submission benchmarks and batch-size limit

`contracts/proof_registry/src/bench.rs` measures Soroban resource usage for
`submit_proof`, `submit_proofs` (1 to 3 records) and `submit_aggregate_proof`
using the repository's `test_support` fixtures (KYC, funds, age, aggregate), so
inputs are identical on every run. Each row resets the budget, performs one
call, then reads CPU instructions and memory from `env.cost_estimate().budget()`
and ledger read/write entries from `env.cost_estimate().resources()`.

```
cargo test -p proof_registry bench -- --nocapture
```

Batches are measured at 1, 2 and 3 records because the contract rejects
duplicate credential types and the fixture catalog has three distinct
single-credential circuits.

## Regression thresholds

The benchmark always asserts that write entries stay within the Soroban
per-transaction limit (50). For release review, set `BENCH_MAX_CPU` and
`BENCH_MAX_MEM` to the previous release's recorded figures plus an agreed margin;
the run fails if any row exceeds them.

## Batch-size limit (`MAX_BATCH_SIZE`)

`MAX_BATCH_SIZE` is a single named constant used by `submit_proofs` and
`submit_aggregate_proof` and is exposed through the read-only `max_batch_size()`
view so clients can preflight a batch without hard-coding the value.

The limit stays at 5. Ledger writes are the cost dimension that is known
without measurement: a batch writes one record per submission, so 5 records
use roughly 5 of the 50 permitted write entries, and the benchmark asserts
that the projection from the 1-record and 3-record rows at `MAX_BATCH_SIZE`
stays under 50. CPU and memory are dominated by one UltraHonk verification per
submission; raising the limit above 5 should only be done after the table
above shows CPU and memory for a 5-record projection with headroom against the
network limits. Changing the constant requires updating the batch boundary
tests (`BatchTooLarge`) alongside it.
